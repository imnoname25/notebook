# Studio 4.3 — Document History & Recovery

Последующая стабилизация и повторная приёмка: [Studio 4.3.1](STUDIO_STABILIZATION_4_3_1.md).
Результаты ниже сохраняют исторический отчёт прогона 4.3.

## Аудит существующей архитектуры

Проверены Prisma `Page`/`PageVersion`, `page-service`, `page-version-service`,
`EditorSaveQueue`, `RichTextEditor`, история, Workspace Tabs/Split View, индекс
`PageLink`, portable JSON/ZIP, резервные копии, корзина и ownership API.

До изменений история сохраняла состояние **перед изменением**. Autosave-снимки
создавались не чаще одного раза в 5 минут, manual/before_restore обходили интервал.
Последовательные одинаковые состояния дедуплицировались по хешу title/content.
Централизованные настройки по умолчанию: 100 снимков / 30 дней. Это история
контрольных состояний, а не журнал каждого символа. При crash терялся payload
очереди в памяти; beforeunload не давал гарантии сохранения.

Save/restore уже выполнялись в транзакции вместе с производными индексами, однако
revision читалась до безусловного UPDATE. Два запроса могли одновременно пройти
проверку и затереть друг друга. До расширения интерфейса добавлена общая
параметризованная блокировка `SELECT ... FOR NO KEY UPDATE OF p`, ограниченная владельцем
и активной иерархией. Revision проверяется после получения блокировки. NO KEY UPDATE не конфликтует с
FK KEY SHARE внутренних ссылок: два взаимно связанных документа могут сохраняться
параллельно без взаимной блокировки. Неверная
revision — HTTP 409, чужая/удалённая страница — 404. Это проверено конкурентными
запросами к настоящей PostgreSQL. Изменения title/content без expectedRevision
теперь отклоняются с 409: старый API-клиент должен сначала получить revision.
Метаданные оформления не требуют revision; существующее UI-переименование передаёт её.

Прежний исторический preview использовал default-schema BlockNote и не понимал
все расширения Notebook. Он заменён чистым read-only React-представлением: никакого
редактирования исторического экземпляра и дополнительных активных редакторов.
Новая система расширяет существующий PageVersion; параллельного серверного журнала
и миграции формата содержимого нет.

При реальном HTTP-тестировании выявлена также гонка API-клиента: отмена чтения JSON
после HTTP-заголовков поглощалась и возвращала `{}` как успешный ответ. Это приводило
к `pages === undefined` и падению PageList после reload. Теперь отмена передаётся
вызывающему коду, некорректный успешный JSON становится ошибкой; отменённый загрузчик
списка не обновляет состояние. Есть отдельный регрессионный тест.

## История и сравнение

История открывается временным полноэкранным рабочим режимом конкретного документа.
Закрытие возвращает тот же workspace; вкладки и соседняя панель не заменяются.
Timeline группирует снимки по дням, показывает точное время, текущее сохранённое rN,
ручные/защитные снимки и результаты восстановления. Есть соседние версии, выбор
произвольной пары, обновление и состояния ошибок.

Первый запрос получает 25 записей **без content**, следующие — по cursor. Полный
JSON загружается только для выбранных состояний, кэш ограничен 8 версиями. Быстрый
выбор отменяет прежние загрузки. Просмотр не отправляет PATCH, не создаёт версий,
не изменяет индекс ссылок. Черновик явно назван локальным состоянием, не сохранённой
версией; сравнение с ним фиксируется при открытии/обновлении, а не на каждом символе.

`history-diff.ts` разворачивает дерево с сохранением путей и родителей. Сопоставление:

1. Уникальные совпадающие blockId.
2. Уникальные полностью одинаковые смысловые поддеревья без blockId; pageId,
   alias, props и inline-форматирование остаются частью сравнения.
3. Для совпавших родителей LIS различает перестановку и обычное смещение после вставки.

Статусы: добавлен, удалён, изменён, перемещён, без изменений. Изменённый и одновременно
перемещённый блок имеет оба признака. Одинаковые неоднозначные блоки и похожие тексты
с новыми ID не сопоставляются наугад. Они показываются как удаление/добавление.
Содержимое сложных блоков сравнивается целиком. Отдельные изменения потомков
отображаются отдельными строками, действия родителя восстанавливают всё поддерево.

Вычисление выполняется Web Worker только для выбранной пары. Старый worker
завершается при смене пары. Ограничения: глубина 64, приблизительно 20 000 блоков;
при превышении — явная ошибка сравнения без изменения документа. Список рендерит
по 60 строк с кнопкой продолжения; JSON поддерева сериализуется только при раскрытии.
Это не полная виртуализация и не семантическое объединение произвольного rich text.

Две колонки доступны на desktop; при ширине до 760 CSS px показывается переключатель
«Старая / Новая». Таблицы имеют собственную горизонтальную прокрутку. Неизвестные
расширения остаются доступны через полный JSON. Исторические internal links сохраняют
pageId/alias и отображаются статически; live widgets и внешние изображения не
выполняют фоновые запросы. Снимок не разрешает автоматически актуальные названия ссылок
и не изменяет backlinks. Палитры Studio не меняются.

## Восстановление документа целиком

После подтверждения контроллер конкретного редактора синхронно запрещает новые
изменения, сохраняет локальную страховку и завершает существующую очередь autosave.
Ошибка autosave прерывает восстановление. Отправляется revision сохранённого
состояния, которое пользователь сравнивал; если перед восстановлением были собственные
несохранённые изменения, используется подтверждённая revision после их flush.

На сервере в одной транзакции:

1. Проверка владельца, блокировка строки и проверка expectedRevision.
2. Обязательный защитный снимок `before_restore`.
3. Замена title/content и увеличение revision.
4. Пересчёт searchText, тегов, PageLink/backlinks и live-widget индекса.
5. Новый снимок `restored`.

Ошибки любого шага откатывают всё. Исторические записи не перезаписываются.
Явные границы восстановления создаются даже при одинаковом хеше: это осознанное
исключение дедупликации. Защитный и итоговый снимки получают приоритет retention
перед обычными, включая импортированные даты из будущего. Они занимают места внутри
лимита; при политике меньше двух записей операция временно требует два снимка.
Обычная возрастная/count retention продолжает действовать при последующих операциях.
Отмена восстановления — восстановление защитного снимка из той же истории.

Timeout/обрыв ответа может означать, что сервер уже завершил транзакцию. Не следует
считать такую ошибку доказательством отката: обновите сравнение. Повтор со старой
revision не перезапишет уже изменившийся документ.

## Частичное восстановление и Undo/Redo

Для существующего блока «Восстановить блок» заменяет его содержимое/поддерево,
сохраняя корневой ID. Сначала сравнивается актуальный блок с ожидаемым состоянием
из diff; устаревшее действие отклоняется. Идентификаторы потомков проверяются на
коллизии со всем оставшимся документом.

Удалённый блок восстанавливается только по явному действию **в конец документа**.
Автоматического предположения о потерянном месте нет. «Вставить копию в конец»
назначает новые ID всем блокам поддерева, сохраняя внутренние pageId и alias.
Родительские/дочерние связи и таблицы копируются целиком. Неподдерживаемый тип не
передаётся редактору наугад: можно просмотреть JSON или восстановить всю версию.

Операции выполняются через штатные транзакции/replaceBlocks/insertBlocks BlockNote.
Работают обычные Undo/Redo и autosave. Перед первым сохранением каждого поколения
восстановления запрашивается ручной защитный снимок текущего серверного документа.
Поколение привязано к payload, поэтому ответ старого in-flight autosave не может
поглотить защиту более позднего восстановления. Backlinks обновляются только после
успешной серверной записи, не при нажатии на историческую ссылку.

Восстановление текстового фрагмента доступно консервативно: один text-inline в обоих
блоках, одинаковые type/props/styles. Общий префикс/суффикс определяются по Unicode
графемам (включая кириллицу и emoji). Возвращается только изменённая середина,
окружающий актуальный текст и форматирование сохраняются. Несколько inline-run,
внутренние/внешние ссылки и несовместимое форматирование не объединяются: предлагается
восстановление блока. Если блок после сравнения изменился, фрагмент не применяется.

## Crash Recovery: IndexedDB

База `notebook-recovery-v1`, stores `drafts` и `metadata`. Ключ:
`[userId, pageId, writerId]`. writerId уникален для экземпляра редактора. Поэтому два
окна браузера не затирают локальные черновики друг друга. Запись содержит title,
полный исходный content, baseRevision, sequence, fingerprint и updatedAt.
В состоянии вкладок/доски и localStorage содержимое документов не сохраняется.

Запись с debounce 300 мс, дополнительно перед HTTP-сохранением, при уходе в background
и размонтировании. sequence предотвращает позднюю перезапись более нового локального
состояния. Подтверждение удаляет запись только при совпадении fingerprint конкретного
payload; новый отличающийся черновик остаётся. Fingerprint учитывает title/content,
а не метаданные журнала. SHA-256 используется в secure context, при HTTP без
crypto.subtle применяется точное каноническое сравнение, не короткая контрольная сумма.

Ограничения: 2 МиБ на запись, 50 записей / 25 МиБ на пользователя. При переполнении
или недоступной IndexedDB показывается ошибка локальной защиты, существующие живые
черновики не вытесняются; серверный autosave продолжает работать. Это ограничение
нужно учитывать для больших документов. До завершения debounce/IDB commit последнее
изменение ещё не защищено от мгновенного crash; очистка данных браузера/сбой диска
также не покрываются этой функцией.

TTL 7 дней: очистка при доступе, запуске приложения, раз в час активной работы и при
записи. Закрытый браузер не исполняет фоновую очистку: данные физически могут оставаться
до следующего запуска. Метаданные вынесены отдельно, чтобы не читать все документы
при каждом autosave. Безграничного журнала локальных снимков нет.

Черновики **не зашифрованы**. userId обеспечивает изоляцию интерфейса, а не защиту
от владельца профиля браузера, DevTools, расширений или XSS. Они не предназначены
для долговременного хранения секретов. При обычном выходе завершаются очереди;
об оставшихся аварийных черновиках запрашивается подтверждение. После успешного logout
хранилище пользователя очищается, BroadcastChannel запрещает старым экземплярам
редактора записывать его заново. Ошибка очистки показывается явно. Чужой аккаунт
не запрашивает эти записи через интерфейс.

При открытии документа отличающийся черновик не применяется автоматически. Есть
«Просмотреть изменения», подтверждённое «Восстановить» и подтверждённое «Оставить
серверную версию». Совпадающее с сервером состояние убирается без ложного предложения.
При конфликте baseRevision сначала предлагается сравнение. Принятый черновик
остаётся в IDB до подтверждённого сохранения; перед записью серверного документа
создаётся защитный снимок. Более свежая серверная revision приводит к 409, не к
молчаливой перезаписи.

При текущей ошибке autosave доступны повтор и «Сравнить с сервером». Сравнение
загружает сервер заново и фиксирует текущий локальный текст. Для конфликта есть
явное подтверждённое переоткрытие **после успешной записи в IndexedDB**, затем обычный
выбор восстановления. Нет автоматического reload для сокрытия ошибки и автоматического
merge несовместимых документов. Ошибка и несохранённый текст остаются доступны.

## Split View, формат данных и миграции

Контроллер и historyPageId принадлежат конкретному pageId. Открытие истории в левой
панели не переводит правую на другой документ. После восстановления обновляется
только целевой редактор; соседняя очередь независима. Временный diff не создаёт вкладки.

Схема Prisma и формат BlockNote JSON не менялись; новых миграций нет. Проверено
развёртывание всех 17 существующих миграций в отдельных чистых PostgreSQL 18 БД.
Production, Docker/CI, Android и Unraid не изменялись.

Portable JSON/ZIP сохраняет формат v4 и совместимость со старыми форматами через
существующие импортёры. История включается существующим параметром includeHistory;
backup содержит серверную историю и вложения. Обычный single-page JSON не содержит
историю. Новый reason `restored` совместим с существующим строковым полем экспорта.
Internal links remap выполняет существующий импортёр. Восстановление/импорт не
превращает исторические ссылки в активные backlinks до восстановления документа.
Локальные IDB-черновики и метаданные crash recovery никогда не добавляются в серверный
JSON/ZIP/backup. Сохранение формата не означает наличие аварийного текста в backup.

## Ручная приёмка

1. Открыть A/B в Split View, изменить A несколько раз и открыть историю A.
2. Выбрать старую/текущую пару; проверить текст, форматирование, таблицу, вложенные
   блоки, перенос и отсутствие PATCH только от просмотра. Соседняя B не меняется.
3. Восстановить блок/таблицу, затем Undo/Redo, вставить копию; проверить сохранение.
4. Восстановить всю версию, найти «Перед восстановлением» и вернуть её обратно.
5. В двух окнах изменить один документ: второе сохранение должно получить конфликт,
   текст остаётся доступен, сравнение с сервером не перезаписывает его.
6. Отключить сеть, набрать текст, дождаться локальной записи; аварийно завершить вкладку.
   Открыть документ: сравнить черновик, восстановить либо явно отказаться. Повторное
   открытие не предлагает уже обработанный черновик.
7. Восстановить блок с pageLink; проверить alias и backlinks после сохранения.
8. Проверить обе темы и узкий/широкий экран физического устройства; прокрутку таблиц,
   клавиатуру, работу второго редактора. Физическая Android-проверка требует пользователя.
