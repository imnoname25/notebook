# Saved Articles — Backup v7

## Контракт

Этап D основан на `7a73650fe79de480ac0e7c28672e1ec62e26ba78`. Миграции БД и новые настройки не требуются. `SAVED_ARTICLE_AUTO_EXTRACT` остаётся выключенным.

ZIP содержит `manifest.json`, `notebook.json` для экспорта или `backup.json` для operational backup и файлы `attachments/`. Каждый локальный файл имеет размер и SHA-256. Экспорт проверяет наличие файла, размер, MIME-сигнатуру и хеш. Изображения статей дополнительно полностью декодируются как WebP с ограничениями размера, пикселей и времени. Повреждение локального изображения прекращает экспорт.

`savedItems[]` сохраняет пользовательские поля, исходный `title`, `titleOrigin`, `sharedTitle`, текст, URL, статусы, даты, теги, метаданные сайта, ключи пользовательских вложений и преобразованной страницы. У v7 обязательно поле `article`, которое содержит объект либо `null`.

| Поле статьи | Содержимое |
| --- | --- |
| `contentVersion` | Версия блоков 1 или 2 |
| `blocks` | Валидированные абзацы, заголовки, цитаты, списки, ссылки и изображения |
| `sourceUrl` | Исходный HTTP(S) URL без credentials |
| `extractedAt` | Дата извлечения |
| `images[].imageKey` | Устойчивый ключ из 64 шестнадцатеричных символов |
| `images[].sourceUrl` | URL изображения для сохранения происхождения |
| `images[].position` | Позиция в статье |
| `images[].attachmentKey` | Переносимый ключ файла либо `null` для несохранённого изображения |

Между блоками и записями изображений требуется однозначное соответствие ключей. Повторяющиеся ключи, позиции, чужие Upload ID, отсутствующие файлы и несовместимый MIME отклоняются. Фактические Upload ID и пути хранения формируются заново. Задания статей, поколения, аренды, токены worker и попытки не сериализуются.

Полный экспорт включает глобальное «Сохранённое», включая архивные материалы. Экспорт отдельного блокнота сохраняет прежнюю область данных. Operational и safety backup используют тот же writer v7.

## Совместимость

| Версия | Импорт | Operational restore |
| --- | --- | --- |
| v1–v5 | Прежние данные архива добавляются с новыми ID | Существующее «Сохранённое» и его файлы сохраняются |
| v6 до этапа A | Заголовок восстанавливается как `legacy` либо `system` | «Сохранённое» заменяется |
| v6 после этапа A | Сохраняются `titleOrigin` и `sharedTitle` | «Сохранённое» заменяется |
| v7 | Дополнительно восстанавливаются статьи и локальные изображения | «Сохранённое», статьи и изображения заменяются транзакционно |

Пороги возможностей заданы независимо. Saved Items и обязательный SHA-256 начинаются с версии 6, статьи — с версии 7. Повышение версии writer сохраняет чтение v6. Старые сборки приложения не обязаны читать v7.

## Восстановление и согласованность

1. Проверяются версия, состав, ссылки, безопасные пути ZIP, лимиты количества и распаковки, SHA-256 и MIME. Для статьи применяется строгая схема блоков и декодирование локальных изображений.
2. Административный restore требует подтверждение `RESTORE`. После валидации создаётся проверяемая safety backup v7. Ошибка этого шага прекращает восстановление.
3. Под общей PostgreSQL advisory-блокировкой файлов пользователя создаются новые файлы и записи. Saved Items, статьи и изображения применяются в одной транзакции.
4. При откате файлы удаляются только после проверки отсутствия их метаданных в БД. Потеря ответа на commit не вызывает удаления зарегистрированных файлов. Если БД недоступна или очистка не удалась, технический журнал требует storage audit без раскрытия содержимого материалов.
5. После успешного commit удаляются прежние неиспользуемые файлы. Safety backup остаётся доступной администратору.

Публикация статьи worker, замена изображений, изменение Saved Item, удаление и очистка Upload используют ту же блокировку, которую writer держит до окончания записи ZIP. Старые задания удаляются каскадно при замене Saved Items. Проверка ID, поколения и аренды не позволяет позднему worker публиковать данные в восстановленные материалы.

Импорт и restore не создают SavedArticleJob. Импортированные задания метаданных сразу завершены. URL архива служат данными происхождения и ссылками. Восстановление и чтение статьи используют локальные файлы. Несохранённое изображение остаётся недоступным. Связь с сервером Notebook нужна для чтения его файлов.

## Восстановление после сбоя

При ошибке операции сначала проверьте уведомления, safety backup и состояние БД. Запустите проверку хранилища в административном интерфейсе. После подтверждения состояния используйте штатную очистку неиспользуемых Upload и незарегистрированных файлов. При необходимости восстановите safety backup с новым явным подтверждением.

Аварийное завершение процесса или отключение питания может оставить незарегистрированные файлы до storage audit. При неизвестном результате commit автоматическое удаление файлов ограничено проверяемым состоянием БД. Application backup охватывает данные одного пользователя. PostgreSQL dump вместе с persistent uploads остаётся способом полного аварийного восстановления сервера.

## Воспроизводимые проверки

Все PostgreSQL-тесты требуют отдельную одноразовую БД и явное разрешение её очистки. HTTP-тесты требуют отдельный запущенный экземпляр приложения с той же БД, `UPLOAD_DIR` и `BACKUP_DIR`. Укажите `TEST_SAVED_HTTP_ORIGIN` с его loopback origin. `SAVED_ARTICLE_AUTO_EXTRACT` должен быть `0`.

```powershell
npm.cmd run lint
npm.cmd run typecheck
npm.cmd test -- --maxWorkers=2
npm.cmd run build
# Только с TEST_DATABASE_URL на выделенной тестовой БД и TEST_RESET_DATABASE=1
npm.cmd run test:integration -- --hookTimeout=30000 --testTimeout=15000
# С дополнительно заданным TEST_SAVED_HTTP_ORIGIN
npm.cmd run test:integration -- src/lib/services/saved-article-backup-http.integration.test.ts
```

Тесты проверяют v1–v6, v7 round-trip, архивные материалы, provenance, теги, даты, вложения, локальные и недоступные изображения, operational restore и safety backup. Негативные сценарии включают испорченный ZIP, SHA-256, отсутствующий файл, неверный MIME, повреждённый raster, дубли ключей, чужой Upload, ошибку записи и транзакции, разрыв соединения PostgreSQL, параллельный экспорт, удаление, очистку и публикацию worker. Результаты конкретного запуска приведены в отчёте этапа D.
