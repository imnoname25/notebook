# Как поймать краткое исчезновение пользовательского содержимого

Уточнение пользователя: исчезает созданное им содержимое; «Сегодня», «Стикеры» и другие
системные пункты остаются. Сбой длится несколько секунд, Console снять не удалось.
Это совместимо с несколькими причинами и само по себе не доказывает потерю сессии.

В текущем коде 401/403 не преобразуются в успешный пустой массив. Обычный выбор страницы
не вызывает `setNotebooks([])`. Дерево занимает flex-область между постоянной навигацией
и нижними действиями; важно отличить пустые данные от нулевой/скрытой области DOM.
Ни одна из этих причин исходного исчезновения пока не подтверждена.

## Добровольная запись в Chrome

1. Открыть Notebook и DevTools → Sources → Snippets → New snippet.
2. Скопировать содержимое [browser-probe.js](browser-probe.js) в snippet и запустить
   **до** попытки повторить сбой. Код запускается пользователем только в этой вкладке;
   установка/обновление Notebook и доступ к серверу для этого не требуются.
3. Выполнить обычные быстрые переходы. После краткого исчезновения открыть Console и
   выполнить:

   ```js
   copy(window.__notebookWorkspaceProbe.report())
   window.__notebookWorkspaceProbe.stop()
   ```

4. Передать полученный JSON для диагностики. `copy` — встроенная функция Console Chrome.
   Для просмотра без копирования: `window.__notebookWorkspaceProbe.report()`.
   Перезагрузка вкладки полностью удаляет скрипт и запись. `stop()` восстанавливает
   прежний fetch и отключает наблюдатели; отчёт остаётся только в памяти до reload.

Записываются до 600 последних событий: размеры и видимость областей, число блокнотов/
разделов/страниц, замена DOM-контейнера, HTTP-категория/метод/статус/время, long tasks и
паузы опроса. Скрипт сам не отправляет запросы, не меняет DOM или данные, не пишет в
localStorage/IndexedDB/файлы и ничего автоматически не загружает наружу.

Не записываются URL сервера, query string, pageId/userId, названия, текст заметок,
HTML документов, заголовки HTTP, cookies, токены и bodies авторизации/документов.
Только у уже выполняющегося GET `/api/notebooks` клонируется JSON для подсчёта элементов;
из него сохраняются исключительно два числа. Сообщения и stack ошибок не сохраняются,
поскольку могут содержать приватный текст: только стандартный тип и координаты ошибки.

## Как различаются случаи

- `tree-response: books=0`, затем `layout: books=0`: сервер действительно вернул пустое дерево.
- `layout: books>0`, но `tree.height=0`/`display=none`/`visibility=hidden`: данные в DOM есть,
  проверяется layout. Это наблюдение, не готовый диагноз причины.
- `shell-replaced`/`tree-replaced`: изменился контейнер; нужно сопоставить с viewport,
  открытием drawer и навигацией. Не всякая замена является ошибкой.
- HTTP 401/403: возможная проблема авторизации, подтверждаемая конкретным запросом.
- `sampling-gap` и `long-task`: задержка главного потока. В фоновой вкладке опрос может
  тормозиться браузером; поле `visible` помогает отличить это от активной работы.

Если весь главный поток заблокирован, скрипт не сможет снять промежуточный DOM, но
зафиксирует паузу после возобновления. Опрос с периодом 250 мс может пропустить более
короткое состояние. Это ограниченная диагностическая запись, не полный Performance trace.

Скрипт проверяется отдельно на изолированном синтетическом DOM и ответах: распознавание
пустого дерева и нулевой высоты, сохранение исходного ответа fetch, отсутствие контрольных
приватных строк в JSON, отсутствие собственных запросов и восстановление fetch после stop.
Повторение: `node scripts/validate-workspace-probe.mjs` (установленный Chrome).
Такая проверка **не является** воспроизведением ошибки Notebook или HTTP E2E приложения.
